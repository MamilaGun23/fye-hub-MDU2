# Demo population tooling

The selected deployment audit route is a **SQL export**. Audit import and previews
run locally without Supabase credentials, network calls or database writes.
Use Node.js 22 or newer. No additional dependencies are needed for these commands.

## 1. Export the deployed audit

Open `database/DEMO_READ_ONLY_AUDIT.sql`, copy its complete contents into the
existing prototype project's Supabase SQL Editor, and run it as `postgres`.
It contains one read-only SELECT. It does not install an RPC, enable an extension,
alter permissions or change application records.

Export the single result row as JSON or CSV. Save it locally, for example as
`.demo-seed/audit-export.json` or `.demo-seed/audit-export.csv`. Create `.demo-seed`
if necessary. Keep it private: it includes student numbers and schema definitions,
but does not select passwords, tokens, real-user names or administrative keys.
The directory is ignored by source control and is outside the served `public/` directory.

```powershell
npm run demo:audit -- --input .demo-seed/audit-export.json
```

If `npm` is not on PATH, use the installed Node executable directly:

```powershell
& 'C:\Program Files\nodejs\node.exe' scripts/demo/cli.cjs audit --input .demo-seed/audit-export.json
```

The importer accepts the raw audit object, Supabase JSON result arrays, stringified
JSON cells, and a CSV result with one `audit` column. Malformed/incomplete reports
stop before generating data. Import creates:

- `.demo-seed/audit.json`: the original deployed snapshot.
- `.demo-seed/audit-findings.json`: schema/catalogue fingerprints, provisioning
  indicators, detected legacy constraints and deployment review checklist.
- `.demo-seed/qualification-review.json`: actual programmes requiring classification.

## 2. Review qualifications

For every programme in `qualification-review.json`, fill `qualification_level`
with one of `undergraduate`, `honours`, `postgraduate_diploma`, `masters` or
`doctorate`; set `max_study_year` to that qualification's valid maximum year.
Keep the actual programme/faculty IDs and names. Review against the real catalogue,
then set the top-level `reviewed` field to `true`. Unknown programmes are rejected,
not guessed. Reimporting the same catalogue preserves this review; a changed
catalogue requires fresh review.

## 3. Generate and check the preview

```powershell
npm run demo:preview -- --batch presentation-2026
npm run demo:check -- --batch presentation-2026
```

Each entry-level UG programme receives 30 first-time Year-1 Student accounts,
20 returning Student accounts and two additional intended mentor accounts.
Advanced Diplomas receive 50 returning Student accounts and two extra mentors.
Other programmes receive 50 returning Student accounts in valid study years. Postgraduate mentor
scenarios require additional separately tracked accounts and explicit supervisor
mappings; the preview does not invent those mappings. All programmes include
the 12 official language preferences, including SASL, assigned separately from
curated fictional names. Nine-digit student numbers encode original entry year,
retain leading zeros and avoid numbers in the audit and the proposed population.
New version-2 previews use `<student_number>@ump.ac.za` for every student and
mentor, and ordinary named UMP addresses for staff. Visible names and labels do
not include batch identifiers or demonstration markers. Protected Auth metadata
and the record registry continue to identify the generated cohort internally.

The named-batch directory contains `plan.json`, `preview.csv`, `summary.json`,
programme/language/cohort count CSVs and immutable input snapshots. No passwords
are generated by preview. `role=mentor` is an intended outcome for historical
appointment scenarios, not authorisation to bypass live approval requirements.
Checks fail if the plan, mappings or schema differ from their recorded hashes.
Repeated preview calls retain the same identities and snapshots.
Frozen version-1 previews remain valid with their original addresses, so resume
and cleanup continue using the exact accounts in the private manifest.

Audit findings still require review of the actual function bodies and policies.
The report is not a declaration that the application is ready for seeding.

## Live insertion

The live commands are implemented against the imported deployed schema. Apply
`database/DEMO_INSTALL.sql` in the existing project's Supabase SQL Editor first.
It is a single transaction containing eight migrations, including the
reviewed 32-programme classification and the minute-by-minute lifecycle job.
For an installation already current through `20261020000000_update_titles.sql`,
apply only `database/20261020010000_natural_account_labels.sql` to enable the new
address formats and natural faculty/event labels. It preserves existing rows,
passwords and frozen input files.
The audited project already has pg_cron installed. Do not rerun the older
`RUN_ALL_LATEST_CHANGES.sql`, which contains destructive table rebuilds.

Copy `.env.example` to the ignored `.env.demo` and configure the existing project
URL and service-role/secret key locally. An optional `DEMO_PRESENTATION_PASSWORD`
sets the shared password for newly created selected presentation accounts (12+
characters); if blank, a random private presentation password is generated.
Bulk account passwords are random. No existing passwords are reset. The project
URL must match `public/supabase-config.js`; live commands refuse another project.

```powershell
npm run demo:check -- --batch presentation-2026
npm run demo:seed -- --batch presentation-2026
npm run demo:verify -- --batch presentation-2026
npm run demo:access -- --batch presentation-2026
```

When Node/npm are not on PATH, replace `npm run demo:seed --` with:

```powershell
& 'C:\Program Files\nodejs\node.exe' scripts/demo/cli.cjs seed --batch presentation-2026
```

The preflight checks the full deployed qualification catalogue, migration version
and demo-audience enforcement before creating accounts. The seeder creates demo
staff first, then 12-account batches with at most three concurrent requests.
Profiles use the Auth UUID and server-only seed RPCs that validate protected Auth
app metadata. Resuming reconciles Auth/profile partial failures, preserves
existing demo edits/passwords and rejects unmarked email collisions. Temporary
network/429/502/503/504 failures have bounded backoff. Schema/permission problems
stop with progress saved. A batch lock prevents two local operations racing.

Scenarios use normal application RPCs inside an atomic idempotency envelope;
all role, faculty, recruitment-date and evidence checks remain effective.
Only restricted service-role RPCs create explicitly marked historical mentor
appointments and completed events/attendance. They cannot create historical
records for pre-existing users. New first-year applications remain unapproved.
New application scenarios are created only in the October–January window.

Private output includes `manifest.json`, `presentation-logins.csv` and
`verification.json`. Verification covers Auth/profile links and email confirmation,
academic fields, at least 50 Student-role accounts per programme, active mentor
appointments, cross-batch matches, total mentor capacity, notification leaks and
selected real sign-ins. Sign-in verification runs serially, retries temporary
service failures with bounded backoff and records failure status/code privately.
The manifest records activity operations and Storage paths.

`demo:access` exercises actual student, mentor, supervisor and admin JWTs. It
checks all ten analytics totals against detail rows, student/mentor authority,
faculty calendars, complete staff-directory pagination, supervisor access to
evidence PDFs and explicit rejection of student access to privileged RPCs.
It saves `.demo-seed/<batch>/access-verification.json` without credentials or
signed document URLs. Missing directory migrations block the affected reads;
independent checks still run. It never creates or resets accounts.

Seed and full verification now require these live access checks to pass before
recording completion. Account/data verification and access verification remain
separate private reports so an outstanding SQL installation cannot be mistaken
for a fully verified application.

The first actual insertion will cover all reviewed programmes after preview and
automated checks pass, in small resumable batches with limited concurrency.
It uses Auth Admin account creation with confirmed fictional emails, followed
by profiles and marked activity. Existing users and existing credentials will
be preserved. A private manifest will track partial creation and dependent records
for resume and preview-first cleanup. No browser-accessible service credential
or general-purpose eligibility bypass will be introduced.

An optional one-programme trial is available, although the user selected all
programmes for the first insertion:

```powershell
npm run demo:trial -- --batch presentation-2026 --programme 1
```

Cleanup previews by default. Inspect the private cleanup report before explicitly
executing it. It checks batch ownership and refuses removal when existing records
reference demo staff. It deletes only tracked records, then the tracked Storage
objects and Auth accounts; it never enumerates arbitrary users for deletion.

```powershell
npm run demo:cleanup -- --batch presentation-2026
npm run demo:cleanup -- --batch presentation-2026 --execute
```

Advanced Diplomas now receive 50 returning students plus two extra mentors, as
confirmed by the user. The manually named medicine programme is a six-year
prototype programme by explicit user choice. The catalogue is kept as-is; no
honours or postgraduate qualifications are invented. The application supports
these qualification levels and supervisor mappings when they are added later.

Auth Admin references:
[account creation](https://supabase.com/docs/reference/javascript/auth-admin-createuser),
[Auth API implementation](https://github.com/supabase/auth/blob/master/openapi.yaml).


## Refresh existing account presentation

The visible identities and activity can be converted without recreating accounts
or changing passwords, academic status, mentor authority or ownership tracking.
Students and mentors use their existing nine-digit student number followed by
@ump.ac.za. Staff use their personal name address. Internal batch markers remain
private and continue to scope verification and cleanup.

```powershell
npm run accounts:refresh -- --batch presentation-2026
npm run accounts:refresh -- --batch presentation-2026 --execute
node scripts/demo/verify-appearance.cjs --batch presentation-2026
```

The first command prepares a private backup and preview, checks every owned
Auth/profile pair and blocks email collisions. Execute checkpoints each account,
updates its Auth address and profile together, replaces visible activity labels
and generated attachments, then regenerates presentation-logins.csv. No password
reset or account recreation occurs. Interrupted execution resumes from its
checkpoint. The reviewed plan and original plan hash remain immutable; the
manifest's appearance overlay supplies the new addresses to seeding, sign-in
verification, access checks, credential exports and cleanup. Private backups,
previews, manifests and password sheets stay outside public/.

Apply 20261020010000_natural_account_labels.sql before creating new batches with
the new identity generator. Conversion of already-provisioned accounts uses the
Auth Admin and scoped profile/content APIs and does not require that migration.
